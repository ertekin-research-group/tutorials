01 — Toolchain Setup Week 1

Getting from a fresh MacBook to a working scientific Python environment, with Git, the Materials Project, and the POTCAR library all wired up.

Goal. By the end of this module, python check_setup.py passes every required check. That script is the definition of "done" — do not move to module 02 until it is green.
Software policy: conda only. No Homebrew. Do not install Homebrew, MacPorts, or system-level scientific packages, and do not pip install anything that exists on conda-forge. This is not a stylistic preference. Two overlapping package managers produce library path and linking conflicts that are genuinely difficult to debug, and they make your environment impossible to reproduce on someone else's machine. One package manager, one environment file, one conda activate.

If you find instructions online that begin with brew install, they are not wrong in general — they are wrong for us. Ask before deviating.

1. Install miniforge

miniforge is a minimal conda distribution that defaults to the conda-forge package repository. We use it rather than Anaconda (bloated, licensing complications) or plain Miniconda (defaults to a different channel).

Download the Apple Silicon installer and run it:

cd ~/Downloads
curl -L -O "https://github.com/conda-forge/miniforge/releases/latest/download/Miniforge3-MacOSX-arm64.sh"
bash Miniforge3-MacOSX-arm64.sh

Accept the license, accept the default install location (~/miniforge3), and say yes when it offers to initialize your shell. Then close the terminal and open a new one.

Check that it worked:

which conda          # should point inside ~/miniforge3
conda --version
Apple Silicon, not Intel. Every Mac in this group is arm64. If you accidentally install the x86_64 build, everything will still appear to work but will run through Rosetta translation at roughly half speed — and you will not notice until your DFT calculations are mysteriously slow. Confirm with uname -m, which should print arm64.

Turn off auto-activation of the base environment

conda config --set auto_activate_base false

This keeps your default shell clean, so you have to deliberately activate the project environment. That is a feature: it means you always know which environment you are in.

2. Create the environment

The file environment.yml in this directory defines the environment. Read it before you run it — it is commented, and the comments explain what each group of packages is for.

conda env create -f environment.yml
conda activate defects

This will take several minutes. conda has to solve the dependency graph and download a few hundred megabytes.

Why an environment file instead of installing packages one at a time? Because environment.yml is a record. It goes in Git, and it means that in six months — or on a new laptop, or for the next student — the same environment can be recreated exactly. A sequence of conda install commands you typed and forgot is not reproducible, and reproducibility is not an abstract virtue here: it is how you tell a real physical result from an artifact of your setup.

Your prompt should now show (defects). Confirm you are running the right Python:

which python         # should be inside ~/miniforge3/envs/defects
python --version     # 3.12.x
You must conda activate defects in every new terminal. This is the single most common source of "it worked yesterday" confusion. If a package suddenly is not found, check which python first — the answer is almost always that you are in the base environment. Later, once VASP is built against this environment's MPI libraries, you will need it activated to run calculations too, not just to run Python.

3. VS Code

Download VS Code from code.visualstudio.com (the Apple Silicon build), and install these extensions from the Extensions panel (Cmd+Shift+X):

  • Python (Microsoft)
  • Jupyter (Microsoft)
  • Claude Code (Anthropic)

Then tell VS Code to use your conda environment: Cmd+Shift+P → Python: Select Interpreter → choose the one whose path contains envs/defects.

The integrated terminal (Ctrl+`) is where you will live. It picks up the selected interpreter automatically, which is one fewer thing to forget.

4. Git and GitHub

Tell Git who you are

git config --global user.name "Your Name"
git config --global user.email "your_netid@illinois.edu"
git config --global init.defaultBranch main
git config --global pull.rebase true

Create a GitHub account and get added to the organization

  1. Create an account at github.com if you do not have one. Use a professional username — it will appear on your published work.
  2. Send Elif your username so she can add you to the group organization.
  3. Once you are a member, create your project repository inside the organization, not under your personal account. This matters: repositories in the organization are owned by the group, survive your graduation, and are visible to the people who need to help you.

Set up an SSH key

This lets you push to GitHub without typing a password every time:

ssh-keygen -t ed25519 -C "your_netid@illinois.edu"
# accept the default location; setting a passphrase is optional
cat ~/.ssh/id_ed25519.pub

Copy the output, then on GitHub go to Settings → SSH and GPG keys → New SSH key and paste it. Test:

ssh -T git@github.com

Clone your repository

mkdir -p ~/research
cd ~/research
git clone git@github.com:ORGNAME/REPONAME.git
cd REPONAME

Copy environment.yml into the repository and make your first commit:

cp ~/path/to/tutorials/01_toolchain/environment.yml .
git add environment.yml
git commit -m "Add conda environment specification"
git push
Commit daily, even when the work is messy. Git is a safety net, not a polished archive. A commit that says "broken, saving progress" is far more useful than no commit. The one thing to keep out of Git is large binary output — WAVECAR, CHGCAR, and vasprun.xml files can be hundreds of megabytes. We will set up a .gitignore for those in module 03.

5. Materials Project API key

The Materials Project is a public database of computed materials properties. We use it for two things: getting starting crystal structures, and later (Week 11) finding the competing phases that set chemical potential limits.

  1. Register at materialsproject.org — free, use your Illinois email.
  2. Go to your dashboard and copy your API key.
  3. Store it. Add this line to ~/.zshrc: 
    export MP_API_KEY="your_key_here"
    then source ~/.zshrc.
  4. Also register it with pymatgen, which looks for its own setting name: 
    mkdir -p ~/.config      # pmg fails if this does not already exist
pmg config --add PMG_MAPI_KEY "your_key_here"
    This writes to ~/.config/.pmgrc.yaml.
Why two names for the same key? The Materials Project replaced its original API with a new one, and the two client libraries look for differently-named settings — PMG_MAPI_KEY for pymatgen's legacy interface, MP_API_KEY for the newer mp-api client. Setting both costs nothing and saves a confusing afternoon later, when a tool you did not write goes looking for the one you did not set.
Never commit your API key to Git. It is tied to your account. Keeping it in ~/.zshrc — outside any repository — is the whole point. If you ever paste a key into a script, stop and move it to an environment variable before committing.

6. The POTCAR library

POTCAR files are the VASP pseudopotentials: one per element, describing how the core electrons are replaced by an effective potential. They are licensed — they come with the VASP license and cannot be redistributed publicly.

Get the library from Elif. Put it somewhere permanent and outside any Git repository, for example ~/vasp_pseudo/.

Two ways you will use POTCARs

By hand. A POTCAR is just the per-element files concatenated in POSCAR order:

cp ~/vasp_pseudo/Si/POTCAR POTCAR                      # one element

rm -f POTCAR                                          # then, for two elements:
cat ~/vasp_pseudo/Ga/POTCAR ~/vasp_pseudo/N/POTCAR > POTCAR   # IN ORDER
Library POTCARs are read-only and cp preserves that, so cat ... > POTCAR fails with permission denied if one is already there. rm -f POTCAR first and the problem disappears.

Through pymatgen. pymatgen can generate POTCARs automatically, but it expects the library in a specific directory layout (with names like POT_GGA_PAW_PBE_54/), which is not the same as the flat <element>/POTCAR layout above. To build the layout pymatgen wants:

pmg config -p ~/vasp_pseudo ~/vasp_psp_pmg
pmg config --add PMG_VASP_PSP_DIR ~/vasp_psp_pmg
export PMG_VASP_PSP_DIR=~/vasp_psp_pmg     # also add this line to ~/.zshrc
This step is fiddly and depends on exactly how the library you were given is organized. If pmg config -p complains, that is normal — bring the error message to the meeting, or work through it with Claude. It is a directory-shuffling problem, not a physics problem, and it is not worth an hour of solo struggle.

Confirm it works

python -c "from pymatgen.io.vasp.inputs import Potcar; \
p = Potcar(['Si'], functional='PBE_54'); print(p[0].keywords['ENMAX'])"

You should get a number around 245 eV. That is silicon's recommended minimum plane-wave cutoff, and you will meet it again in module 04.

POTCAR order must match POSCAR order. Always. If your POSCAR lists Ga N, your POTCAR must contain gallium first, then nitrogen. Get this backwards and VASP will run happily to completion and give you a completely meaningless answer, with no error message. This is the single most expensive silent mistake in VASP, and it is worth developing a reflex of checking: 
head -1 POTCAR
grep -c "End of Dataset" POTCAR    # how many elements are in there

7. Verify everything

Run the check script in this directory:

conda activate defects
python check_setup.py

It tests each piece independently and keeps going after a failure, so one run tells you everything that is wrong rather than one thing at a time.

The last two checks — MPI and gfortran — are allowed to report warn at this stage. Those belong to module 02. Every other check must say ok.

8. Week 1 deliverable

Commit to your repository:

  • environment.yml
  • A Jupyter notebook that imports ASE and pymatgen, builds a silicon structure with each, and prints the space group. Three cells is plenty — the point is to demonstrate the toolchain works, not to do science.
  • A short notes.md recording anything in this module that did not work as written, and what you did instead. This is not optional. These instructions were written before anyone followed them on your specific machine, and the corrections you find are how they get better for the next person.

Also confirm with Elif that your cluster account is active. You will not use it until Week 12, but there is no reason to discover a problem then.
